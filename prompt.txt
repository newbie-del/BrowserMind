==================================================
WHAT BROWSERMIND IS
==================================================

BrowserMind is a collaborative AI browser-workflow SaaS.

A user gives BrowserMind a natural-language goal. BrowserMind:

1. Understands the goal.
2. Creates an execution plan.
3. Converts the goal into a visual workflow (a flowchart of steps).
4. Lets the user/team review and edit the workflow.
5. Assigns steps to humans or to BrowserMind's AI agent.
6. Publishes a workflow version.
7. Executes it using an AI agent that controls a real web browser.
8. Shows the browser live while it works.
9. Verifies important actions/results.
10. Recovers from failures where possible.
11. Pauses for human approval when required (submissions, sending emails, etc).
12. Produces results and an audit trail.
13. Saves useful workflow/task memory for reuse.
14. Allows workflows to be reused or scheduled.

THREE DEMO SCENARIOS (all three must work by the end):

A. STUDENT FORM APPLICATION
   "Fill my JEE application."
   User uploads Aadhaar, Class 10 marksheet, Class 12 marksheet, photograph,
   signature, category certificate. BrowserMind extracts info from each
   document, understands the target form's fields, matches each document to
   the correct upload field (a "photograph" field gets the photo file, a
   "signature" field gets the signature file — never a random file), fills
   text fields, uploads the right files, pauses for human approval before
   final submission, and hands off OTP/CAPTCHA to the human.

B. TPO / PLACEMENT WORKFLOW
   "Find suitable software engineering opportunities this week."
   Search sources → collect opportunities → extract info → check eligibility
   → deduplicate → verify → shortlist → produce a report/email.

C. TECHFEST SPONSORSHIP WORKFLOW
   "Find companies that could sponsor our TechFest, verify relevance, prepare
   personalized emails, and don't send anything without team approval."
   Research → collect info → verify relevance → dedupe → shortlist → draft
   personalized emails → checker → team review → human approval → send.
   Different teammates can own different steps (Coordinator A = research,
   Coordinator B = verification, Coordinator C = outreach review, Team Lead =
   final approval, BrowserMind = browser research/execution).

BROWSEROS — READ-ONLY REFERENCE FOR CONCEPTS. BrowserOS is a Chromium fork

browser-engine code and desktop coupling are NOT reusable inside a web SaaS
and must NOT be built, compiled, or run as part of BrowserMind. What IS worth
reading and borrowing as *ideas* (not code to execute):
  - the shape of its agent tool set (navigate/click/type/scroll/extract/tabs)
  - its MCP tool-naming conventions
  - its action-timeline / activity-log UI concept
  - its scheduled-task concept
Do not attempt to convert BrowserOS into a multi-tenant remote service. That
is a separate, enterprise-scale infrastructure project (comparable to what
companies like Browserbase or Browserless sell), not something to build from
scratch here.

==================================================
REMOTE BROWSER + LIVE VIEW — USE A PROVIDER, DO NOT BUILD INFRASTRUCTURE
==================================================

BrowserMind needs the user to see a live, remote browser session in the web
app, with proper session isolation between users. Do NOT build this
yourself (no custom Docker-per-user orchestration, no custom WebRTC/CDP
streaming stack, no custom multi-tenant isolation layer). That is a
distributed-systems project on its own and will consume the entire credit
budget without a working result.

Instead, integrate an existing remote-browser provider and connect Browser-Use
to it:
  - Preferred: Browserbase (has a free tier, gives isolated remote Chromium
    sessions, an embeddable live-session view/iframe, and built-in session
    replay/inspector) — or
  - Alternative: Steel (open-source, self-hostable if we outgrow a hosted
    free tier).

Browser-Use already supports connecting to a remote CDP endpoint — point it
at the provider's session instead of a local browser. This gets us live view,
isolation, and replay without building any of it ourselves.

If neither provider works for a specific requirement, stop and ask before
building a custom alternative.

        matching that happens to handle all three scenarios.
RULE 19: Do not attempt to bypass CAPTCHA. Hand off to the human.
RULE 20: Never expose credentials or provider API secrets to the LLM or the
        frontend.

Before writing new code, ask:
  "Does an existing file/component/service already solve this?"
  "Does Browser-Use already provide this?"
  "Does Workflow-Use already provide a useful reference for this?"
  "Does the chosen remote-browser provider already solve this?"

SECURITY / APPROVAL
==================================================

Sensitive actions require a policy/approval gate: final application
submission, sending external emails, payment, destructive actions, account
changes. OTP and CAPTCHA always require human intervention — never attempt
to bypass them. Credentials must never be exposed directly to the LLM; use
the remote-browser provider's authenticated-session mechanisms instead.

==================================================
EXECUTION UI
==================================================

While an agent runs, the user should see: current workflow step, the live
remote browser (via the provider's embeddable view), current URL, current
action, completed/failed steps, recovery attempts, approval state, and an
activity timeline (e.g. "✓ Opened website / ✓ Filled personal details /
● Uploading photograph / ○ Verify / ○ Approval / ○ Submit").
